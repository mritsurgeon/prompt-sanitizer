AI Safe · engine reference

Architecture & data flow

One engine, two front ends, no backend. Everything below — parsing, detection, judgement, classification, sanitization, the policy call — runs as plain TypeScript, either in the tab you opened or in the extension watching the composer.

The short answer

Are you running models?

Yes, selectively

One: GLiNER small v2.1, as the confirmer. It never sees a normal scan — the rules do the finding, and the model is woken only for the calls they could not settle. It is not loaded at startup, and if its weights were never provisioned the engine falls back to a deterministic pass and keeps working.

Your content still never leaves the machine — there is no server to send it to. The single request either front end makes is for the model weights: the app from its own origin, the extension from the origin that provisioned them, and only when a scan escalates. Those files are downloaded once at install time by npm run provision:model. Serve the app offline and it keeps working.

Stage by stage

What happens to one scan

The gate is the load-bearing part. On a normal scan nothing lands in the medium tier, so the confirmer is never constructed, loaded or called — measured at 0.00 ms of added cost. It runs only when the fast path genuinely could not decide, and even then it sees a ±160-character window per candidate, never the document.

The confirmer

What the model is allowed to do

Action Allowed Why
Confirm a finding yes Promotes an uncertain call to certain
Relabel a finding yes The rules guess a category from shape; the model knows Nokia Bell Labs is a company, not a person
Recover a candidate scored too low to show yes A name in no word list is invisible to the rules — this is the false-negative half
Discover an entity nobody proposed yes Only if capitalised, and outside a span the rules already turned down
Delete a finding the rules called no The model sees ~320 characters; the rules saw the document. An unnecessary redaction is an annoyance, a deleted finding is a leak

Two surfaces

Where this engine runs

The obvious design was a localhost bridge, and it was not built. A background service owning the engine would have been the first server this project ever had, and “nothing leaves your device” is currently true because there is nowhere for it to go. Running in-process also removes the failure mode where protection silently stops working because a service is not running.
The enforcement point

What happens when you hit send

Two moments are observed, and nothing else. No keystroke scanning, no mutation observers on the composer, no polling. Typing with the extension installed is byte-for-byte the same as typing without it — and when a redesign moves a composer somewhere the adapter cannot find, the script says so in the console rather than degrading quietly to no protection.

Policy

Findings in, a decision out

Detection answers what is here. Policy answers what should happen about it, and those are different questions with different owners — the same finding warrants a block in one organisation and a shrug in another. policy.ts lives in the engine rather than the extension, so the app, the extension and the tests all reach the same verdict from the same rules.

What was found Default Why
A live credential, certain block The only thing that stops somebody outright
Personal data, certain warn Worth a pause, not a wall
Roadmap, pricing, internal plans warn Same — the user knows their context better than the rules do
Hostnames, case and customer numbers warn Same
Anything the engine is not certain about warn at most A “possible” name must never be the thing that stops somebody working, whatever the policy says about its category
The engine could not be reached warn, and say so “We found nothing” and “we could not look” are different states; collapsing them into a quiet allow is how a safety tool ends up protecting nothing
Deliberately not maximal. A tool that blocks constantly gets switched off, and then it protects nothing. So only live credentials stop a send outright, everything else asks, and the primary action always moves the user forward — Mask it, Use fake names — never “you may not do this”.
Boundaries

What never leaves the device

  • The original text and the original file bytes — held in memory, never uploaded, never written to disk.
  • Findings, scores and signals — computed and discarded when the tab closes.
  • The prompt improver only ever sees the sanitized text; the original is not passed to it.
  • The feedback dataset stores the shape of an assessment — counts, signal ids, topics — never raw content, and has no transport of any kind.
  • Cleaned files are built in memory and handed to the browser’s download; the original is never modified.
  • In the extension, the content script keeps no finding and no text beyond the call it made — it asks the worker and renders the answer, inside a document the AI site’s own scripts share.
  • The worker records counts and latencies only: how many checks, how many blocked, a rolling window of milliseconds. Never content, never a URL, never a page title.
  • Edit in AI Safe hands the prompt over through the extension’s session storage, never the URL — a query string ends up in history, in the omnibox and in anything sampling open tabs, which is the exposure this tool exists to prevent.
  • The extension’s one network request is for the model weights, from the origin that provisioned them. Executable code always ships with the extension: MV3 forbids fetching script, and loading code over the network would defeat the point of the CSP.
